# 0.6.1

## GS2: objects made with `new` (roadmap #7)

The VM ran neither `OP_INLINE_NEW`, `OP_NEW_OBJECT` nor `OP_MAKEVAR`, so
the GUI control blocks and the static var in the 2019 Delteria backup
(Graal_analysis PR #625: 97 blocks, 1 `new TStaticVar()`) compiled but
did nothing. Now:

- `new T(name)` and `new T()` make an object of type `T` under the global
  object, named `name` (or `unknown_object#n`). Its variable holds the
  object, so the bare name reaches it anywhere, and a variable it is kept
  in (`temp.o = new TStaticVar()`) reaches the same members.
- `new T("name") { … }` runs its block with the new object as `this`;
  unqualified names inside are the object's (a name the level has stays
  the level's). The object then goes to `addcontrol(name)` on the host,
  as the reference compiler encodes it. Drawing the controls is the
  host's job: `Machine::objects()` lists each object and its type, and
  `Machine::object_var(object, name)` reads its variables.
- `with` takes those objects, and any variable path (`with (this.part)`
  works on `this.part.*`). It used to skip a block on a path.
- `obj.objecttype()` gives the type and `obj.destroy()` removes the
  object and its variables.
- `makevar("this.a" @ i)` is the variable the text names, resolved as the
  same name written in the script would be.

A second `new` with a name that is already an object keeps its variables,
as a GUI control set again does. That, and the anonymous name, are
Seihai's choices **[seihai]**.

## GS2: `triggeraction` and `triggerserver`

`EffectHost` turns `triggeraction(x, y, action, params…)` into
`Effect::TriggerAction` (the action lower-cased and the parameters joined
with commas, as GS1 does), and `triggerserver(type, name, params…)` into
a trigger action at (0, 0) named `serverside` with `name,params…`, the
form GServer-v2 hands to a weapon's `onActionServerSide` **[inf]**.

## Server trigger actions, `PLO_TRIGGERACTION` (48) (#106)

`protocol::parse_server_trigger` decodes 48 (GSHORT player, GINT3 NPC,
half-tile x and y, then the action split at the first comma, as
Graal_analysis `protocol/payload-and-trigger-205r2.md` reads the 2.05
handler) into a `ServerTrigger`. `SessionState::triggers` collects them
for builds whose receive set has 48 (2.03 on), and the client session
hands them to the game through the new `Live::triggers`. The field order
is **[srv][2.05]**; the lab capture from a real 2.22 and 5.12 that #106
asks for is still open.

## Script delivery

`delivery::Prepared::gs1` compiles a client part that strict GS1 refuses
(GS2 call syntax such as `setshape2(2, 2, {…})` next to `if (created)`)
as `Language::Detect` reads it, with the legacy quirks; the GS1 errors
are kept when that fails too. Such parts used to go to GS2 builds as a
stub.

## Docs

`cargo doc` builds without warnings, with and without `audio` (48 were
left: links to private or hidden items, and `[inf]`-style tags read as
links). CI now runs it with `RUSTDOCFLAGS=-D warnings`.

## GS1 to GS2: `#s(name)` on a plain string

`#s(door)` used to be refused. A plain GS1 string is a player flag, which
`setstring` sends as `client.gs1_door` and seihai-gserver keeps as
`door`, so it now reads `player.door`, the same way a plain flag read
lowers (lab 2026-11-13 for flags; for strings **[inf]**). `local.` and
`server.` strings, and a plain name built at run time, are still refused.

## Fuzzing (#80)

Two new targets: `session_apply` (every server→client decoder behind
`SessionState::apply`, as 2.05, 2.22 and 5.12) and `gs2_exec` (the GS2
executor on any bytecode the reader takes). All 13 targets ran for four
minutes each with no crash. `gs1_parse` found a timeout: commas nested in
parentheses retried each other's `, b in |lo,hi|` look-ahead, so the GS1
parse time grew about sevenfold per level. The parser now remembers a
comma where the look-ahead failed, and the regression test parses twelve
levels at once.

## Compatibility

New items and new fields in `SessionState` and `Live`, both built with
`Default`. No signature changes.
