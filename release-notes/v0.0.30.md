The GS2 executor now runs the VM read from every Windows client from 4.04r2 to 6.03r7, and opcode 54 runs.

## Scripting

- **Opcode 54** (5.00r7 on) now runs. It is `obj.(name) = value` in one step: it pops the value, the member name and the object, and stores the value. Before, it was skipped with its three values left on the stack.
- **4.04r2** (Windows) gets its own profile. It has 4.20r6's opcodes and rules, but it runs on x86, so a shift count is taken mod 32. Before, it borrowed 4.20r6's PowerPC shifts.
- **5.24r4, 5.30r3, 5.31r4, 6.00r2 and 6.00r4** share a new `5.24r4` profile. This is the rewritten VM of the 6.x clients:
  - opcodes 48 and 49 are skipped, as in 6.x;
  - the value stack still stops at 10 000;
  - `x ^ 0.5` is still a double-precision square root.

  Before, 5.24r4 to 5.31r4 ran 5.00r7's VM, and 6.00r2 and 6.00r4 ran 6.03r7's, which has no stack limit and a single-precision root.
- **5.12** is confirmed to run 5.00r7's VM unchanged.
- **Windows 6.03r7** is confirmed to match the Linux 6.03r7 read.
- **`waitfor` timeout:** a `waitfor` that times out gives 0. This was assumed before and is now read from 5.12 and 6.00r2. No behaviour changes.

## Docs

- `documentation/gs2-vm-versions.md` lists every client build with the VM that was read for it, or the VM it borrows and why, and documents opcode 54 and the `waitfor` timeout. The Mac 4.04r2, Mac 5.12 and 7.x VMs are still unread.

## Checks

- `tests/gs2_vm_versions.rs` covers opcode 54, the 4.04r2 shifts, the 10 000-value stack up to 6.00r4, the 5.24r4 root, the end of opcode 49 after 5.12, and the `waitfor` timeout.
